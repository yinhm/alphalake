# 财务存储与导出重设计：实测问题、目标与实施规格

状态：2026-09-25 已发布schema52主库及SQLite v3，实际结果见[切换验收](financial-storage-cutover-20260925.md)。本文以下问题测量与阶段记录保留为设计时基线，不代表当前数据库。无源数值/BLOB副本，原网页和估值公式不改。

## 1. 改造前基线及测量口径

本轮历史同步已取消，已提交包保留，未完成包回滚；原始缓存、主库 WAL、最近一份同步前备份及审核记录均保留。取消运行不能记为全量成功。网页仍读取此前 SQLite，本轮没有发布新网页数据。

改造前主库 `workspace/alphalake.duckdb`：

|---|---:|

| 源字段行 `fundamental.provider_fact` | 86,170,952 |

进一步盘点：36,196,050 条诊断来自 83 次运行的 `provider_zero_ambiguous`，其余所有诊断合计仅 61 条。`pragma_storage_info` 显示源表数据段引用 5,720 个有效块（约1,430MiB）、标准表694块（约173.5MiB）、诊断表5,209块（约1,302.25MiB）。这是数据段引用块的量级，不是含索引的独占表大小；块可能共享，不能简单相加后把全部差额都归因于索引。实际 DuckDB 版本为1.5.5。

## 2. 根因，按影响顺序

1. **源层把一条公司记录展开成数百条有索引的字段行。** `schema.sql` 的源表有 16 列、主键及四列复合唯一约束。每个值重复关联证券、报告期、文件、两个哈希字符串、运行和时间；同一 float32 同时保存 DOUBLE 与 UBIGINT 位值。字符串能压缩，但行数、索引、事务、连接与反序列化成本不会因此消失。
2. **将源字段级唯一性放在巨大索引上维护。** 当前写入还执行多轮暂存、去重、计数、反连接、删除及 ON CONFLICT。重放遇到相同行时仍更新运行和时间。包级缓存跳过有帮助，但缓存失效、身份重算时仍回到这个昂贵路径。
3. **标准层再次持久化字段长表。** 20 列重复描述每个值的共同报告身份及血缘；当前全字段物化每三个源字段一批，每批执行源表连接、规则判定、标准表协调。控制了单批内存，却引入大量重复扫描与连接，不能视作速度优化。
4. **拒绝诊断按运行追加，稳定拒绝没有复用。** `fundamental_materialize.go` 把拒绝逐字段写入 `meta.validation_result`，并拼接版本、证券、字段、公告等文本。已有 3,620 万行；诊断不能成为比业务数据增长还快的另一个事实库。
5. **导出路径以进程为查询单位。** `export_alphalake_sqlite.py` 按公司和历史窗口调用 CLI，反复打开同一个 DuckDB；随后逐单元格写标准事实与血缘 JSON。历史窗口已有局部缓存，仍不是全批次一次查询。整库 SHA-256 还引入一次与估值财务无关的全文件读取。

DuckDB 官方说明：主键/唯一约束会维护 ART 索引，影响写入并消耗内存；复合索引并不自动提供普通单列选择性索引扫描的收益，索引内存也存在不能像数据页一样回收的限制。见 [Indexing](https://duckdb.org/docs/lts/guides/performance/indexing)。因此重点应是减少被索引对象的数量，而非反复重连释放内存。

## 3. 历史源存储原型（1ac15ea；BLOB方案已否决）

真实输入：`gpcw20260630.zip`，SHA-256 `388a2ba8c65b40a687a26f9244ac8c616d99522efa1bc9e39df16aa935da7dee`。

环境：单 Go 执行线程、DuckDB 单线程/512 MiB，独立服务进程硬上限 1 GiB，无 swap。顺序执行，未清空操作系统页缓存；读数是重新打开数据库后的有缓存读取，不是冷磁盘性能。时间含 Appender/事务、CHECKPOINT 和关闭，另列读取及 Go 解码；解析 ZIP 单独计时，不计入写入时间。

按代码排序取 512 条公司记录、584 个源位置，三个独立新库重复三次，中位数：

| 物理方案 | 持久行数 | 文件大小 | 写入并落盘 | 全部源位值读取及解码 |
|---|---:|---:|---:|---:|
| 当前索引字段长表及现有协调函数 | 299,008 | 18.01 MiB | 2.688 秒 | 0.321 秒 |
| 每记录一行、584 个 UINTEGER 位值列 | 512 | 3.01 MiB | 0.158 秒 | 0.039 秒 |
| 每记录一行、原始位值 BLOB | 512 | 1.26 MiB | 0.026 秒 | 0.008 秒 |

BLOB 三次文件大小为 1.26–1.76 MiB，表中取中位数，不掩盖块分配差异。两种候选均维护记录级唯一约束。宽位值表写入约快 17 倍，BLOB 约快 105 倍；**这些倍数只属于这个源写入实验**。

完整包有 5,572 条记录，其中 5 条为完全相同的重复记录。对 5,567 条不同代码记录、3,251,128 个位值，候选单次结果：

| 候选 | 文件大小 | 写入并落盘 | 全位值读回 |
|---|---:|---:|---:|
| 位值宽表 | 9.51 MiB | 0.374 秒 | 0.194 秒 |
| 位值 BLOB | 7.26 MiB | 0.145 秒 | 0.081 秒 |

完整去重包的现有索引长表，在相同512MiB查询预算下于提交时内存分配失败，28.12秒退出，进程峰值约851MiB；没有触发系统OOM。失败记录保留，不给失败运行计算“成功吞吐”。这一结果比小样本倍数更说明当前设计的扩展风险。

本包 ZIP 为 5.49 MiB，解压文件 12.47 MiB。解析耗时约 0.12–0.15 秒，所有参与记录的全部位值逐一回读相等。此实验针对源维护，保留包内市场范围，不代表默认沪深业务分母；基准不执行证券身份解析、公告关联、标准物化或 SQLite 导出。

候选用批量直接追加，包级元数据仅以 artifact 标识引用，未在原型中创建完整发布台账；基准证券ID为局部占位，不冒充真实身份验收。旧表用当前完整协调函数，因此既体现物理形态差异，也包含不同发布算法的成本，不把这些数称为单纯 SQL 引擎倍数。标准宽表、查询投影、冷启动及端到端导出仍须另测。完整重设计的加速比例尚未知。

试验还遇到了重复代码唯一约束拒绝，原型已改为对相同位值去重、冲突即拒绝，并记录重复数。**生产源记录必须以包内行序定位所有原文记录**；标准化阶段才能按已有规则折叠相同重复、拒绝冲突。不能把原型的去重表直接当作原始证据存储。

## 4. 推荐的最终表形态

保持 DuckDB 主库及现有分层，不新建另一套数据库服务，也不引入散落的 Parquet/对象清单体系。用户已明确取消源BLOB层。采用“不可变ZIP → 内存解析及语义校验 → 标准快照宽表”；库内源层仅保留轻量记录定位与治理关系，不保存第二份源数值，无BLOB、源位值宽表或字段长表。

| 表/对象（拟定） | 粒度与主要内容 | 用途 |
|---|---|---|
| `meta.artifact` | 每原始文件版本一行；SHA、路径、取得时间 | 继续复用原始证据目录 |
| `fundamental.source_record` | 每 artifact＋原文行序一行；代码、市场标记、字段数，不含数值 | 定位ZIP中的未知字段、源零、非有限位值、重复及冲突原文；读取时校验文件和记录边界 |
| `fundamental.provider_record_resolution` | 每来源代码/版本的身份结论 | 复用当前治理语义；身份修正不重写几百个原始值 |
| `fundamental.provider_filing_link` | 每记录版本的公告关联与拒绝原因 | 复用现有机制，关联一次而非每字段重复关联 |
| `fundamental.statement_snapshot` | 每公司/期间/范围/币种/公告及来源版本一行；审核后的标准字段列 | 财务查询和估值的主数据路径 |
| 标准字段目录与映射 | 字段单位、期间、规则、零值政策及生效范围 | 全目录驱动生成标准列与投影；业务层不认识源位置 |
| 紧凑诊断状态及检查运行 | 记录/规则版本/输入内容下的拒绝字段集合；运行关联检查批次 | 拒绝详情只保存一次，复验不重复展开同一文本 |

源包的文件哈希、报告期、格式及解析版本在包级元数据保存一次；记录只引用小整数标识。原始位值仅存在于ZIP中的原始文件，按现有小端解析规则按需读取；解析缓冲不持久化。

标准快照的列使用通用名称，例如 `revenue_cumulative`、`reported_ebit`；NULL 表示没有可消费值，拒绝状态由关联诊断明确区分。初始保持现有标准 DECIMAL 精度，不趁优化偷偷改成 float32。每股、比例、日期与计数按目录保持类型与期间；每个字段的期间含义来自目录，不能用一个行级“累计”标签覆盖混合字段。

三张报表作为明确列投影的视图/查询接口；一家公司一份报告的身份、范围、公告与血缘共享。无需三次重复存储共同元数据。字段级血缘默认由“快照→源记录→字段映射版本”推出；特殊附注/多来源的审核分量继续独立显式保存，不伪装为整行都来自同一文件。

原始数值未变但归属、映射或公告证据变更时，只重算受影响标准记录；旧版本及审核关系不因快照重建而消失。原文 ZIP 仍是不可变证据，数据库的源投影可验证重建。第一版不做跨版本逐单元格去重：先消除 584 倍行数，避免引入昂贵的细粒度版本连接；若公司整行版本重复显著，再实测是否采用记录内容复用。

宽表不是 BLOB：业务 SQL 直接选择所需标准列，利用列存投影，不把解码成本转嫁给网页。审核、重算和源位核对通过文件哈希与原文行序回读ZIP，禁止增加源BLOB缓存。

## 5. 最短入库及导出路径

### 入库

1. 有效缓存与已发布包版本相同且解析/身份规则未变：跳过 ZIP 展开及源表写入，只保存必要运行记录。变更身份规则不能被包哈希跳过。
2. 新包解析一次；包内长度、重复、位值、身份及范围校验按记录批量完成，保留拒绝证据。
3. Appender 批量写轻量源记录定位，包级发布事务绑定记录、版本及完成检查点。只对记录级键维护必要约束，移除海量字段级主键与复合索引。
4. 公告关联、映射和零值规则按记录批次一次处理；标准列由共享目录生成，整批写入标准快照。规则变更按依赖重算，不用数百字段轮流扫描整张源表。
5. 对稳定拒绝保留唯一内容及可查询的运行/批次关联；状态解决后结束有效区间，历史失败仍能追溯。不是删除旧失败日志来制造体积改善。

### 查询与 SQLite 导出

1. 一次打开主库、一个只读快照；一次取出请求证券集合与整个历史范围。把证券/期间过滤推进标准快照查询；不先展开全市场全部字段再过滤。
2. 年度、单季和 TTM 基于选中的宽表列集合计算，保留现有期间规则和缺项拒绝。只在需要现有结构化返回时，对已经筛选的小结果展开为字段行。
3. 一次 Go CLI 进程向现有 Python 导出器提供有界流式结果；Python 复用 SQLite 单事务和批量写入。暂不新增 SQLite DuckDB 扩展或数据库服务依赖。
4. 共享血缘进入导出元数据/关联表；目标原 SQL 必需的表和列保持不变。移除导出器内部重复财务快照与巨大逐格 JSON 前，先同步所有消费者和缺项报告。
5. 以财务发布版本/内容签名＋事务读取校验一致性，避免每次全文件哈希。已有审计要求整库哈希时在发布阶段一次生成，不冒充仅财务内容签名为整库哈希。
6. SQLite 临时文件验收后原子发布；不完整结果不覆盖既有可信快照。来源缺失与原 SQL 定义不等价仍明确拒绝，不用性能改造绕过网页准入。

索引只针对实测瓶颈添加。记录级唯一约束保留；标准快照排序优先考虑证券、期间/版本，利用列存区间裁剪。全市场期间扫描与单公司历史读取同时测量，再决定具体排序和索引，不按直觉堆索引。参见 [DuckDB Schema 性能指南](https://duckdb.org/docs/current/guides/performance/schema)。

## 6. 性能是发布门槛，以下不是已实现指标

固定本机、单线程、1 GiB 进程硬上限；冻结本地全部已到期包、身份目录、CNINFO 关联和映射版本。区分缓存校验、解压解析、源写入、标准物化和导出各段；每项至少三次，报告中位数及最差值。读取分别测进程冷启动和进程复用，未清页缓存不得称冷磁盘。

拟定首轮硬门槛：

| 工作负载 | 发布门槛 |
|---|---|
| 当前全部已到期缓存源入库 | ≤60 秒；无逐字段持久化 |
| 全量标准物化 | ≤60 秒；保留全部拒绝分母 |
| 单期更新＋受影响标准重算 | ≤5 秒 |
| 相同输入重放 | ≤3 秒；源/标准数值及拒绝内容零重复写入 |
| 单公司完整历史标准查询 | 复用进程≤100毫秒，冷进程端到端≤1秒 |
| 沪深全市场默认10年/8季 SQLite 财务导出 | ≤60秒；含输出落盘及验收；无逐公司子进程 |
| 财务数据/索引/诊断的当前工作集 | ≤对应全部版本解压源体积的3倍，争取2倍；整库其他域另列 |
| 资源 | 全程RSS≤1GiB；失败/取消不得破坏已发布数据 |

对照必须使用相同证券、期间、版本集合与输出字段。缓存只有当前版本而主库含更多版本时，补齐分母，不用删历史得到漂亮比值。压缩旧审计证据可移至 workspace 的归档文件并用哈希/清单引用，但必须计入总存储报告，不能隐藏转移量。达不到门槛就返回剖析与改法，不以“能跑完”验收，也不把原型 105 倍宣传成完整系统提升。

## 7. 实施次序与停止条件

1. **先冻结当前基线、补齐端到端 benchmark。** 已完成源存储历史基准、当前库盘点、隔离宽表重建及全部标准单元格对比；完整SQLite基准仍未完成，不冒称生产改造验收。
2. **替换源表。** 新库从不可变包重建轻量记录定位；保留身份、冲突、运行和原始行定位。逐位核对并验证相同重放、损坏拒绝、重复/冲突、取消和事务回滚。先保存不可重建审核记录。
3. **替换标准物化和读取。** 保持金额、期间、NULL/拒绝、公告时点及血缘结果等价；旧字段长表不作为长期兼容路径保留。目录、业务调用、测试、skill和文档同步更新。
4. **替换批量导出。** 同样输入比较 SQLite 必需表和结构化缺项报告，验证安克、茅台和全市场分母；财务口径不足仍单独列明。
5. **最后发布及回收旧库。** 新库重开、内容对比、性能与失败测试全部通过后，原子切换唯一主库并轮转最近一份备份；删除记录留路径、哈希及理由。

当前不再为旧字段长表继续增加批处理补丁。也不混入 WACC、估值政策、前端或新的财务取证范围。成功标准是完整且可追溯的同一批数据明显更小、入库与导出达到硬门槛，而非仅减少某张表的行数。

## 8. 当前隔离重建与复验

当前代码提供三个独立工具，**不接管 `alphalake` 正式同步/查询，不修改原库**：

以下为隔离服务内执行的命令；重建使用DuckDB 512MiB，对照同时打开两库使用256MiB，进程硬上限均为1GiB：

```bash
ALPHALAKE_DUCKDB_MEMORY_LIMIT=512MiB go run ./cmd/rebuild-financial-storage --source workspace/alphalake.duckdb \
  --output /tmp/financial-candidate.duckdb --root workspace --audit /tmp/financial-audit
ALPHALAKE_DUCKDB_MEMORY_LIMIT=256MiB go run ./cmd/check-financial-rebuild --previous workspace/alphalake.duckdb \
  --candidate /tmp/financial-candidate.duckdb --query-code 300866
go run ./cmd/financial-storage-bench --database /tmp/financial-candidate.duckdb \
  --root workspace --output /tmp/financial-benchmark
```

上述命令必须在独立systemd服务、1GiB硬上限内串行执行，不直接在交互终端做大库任务。输出数据库及目录必须不存在。候选版本52明确拒绝由当前schema51运行时打开；不可自行覆盖主库。旧源存储实验使用历史提交 `1ac15ea` 复现，当前基准不再提供BLOB选项。
